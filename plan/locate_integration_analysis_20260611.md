# LocateAnything 集成分析与方案建议

> 日期：2026-06-11
> 作者：Claude（基于对仓库代码、configs、visual/ 下 eval 结果的实际调查）
> 主题：回答两个问题——(1) Locate 特征怎么取才能真正增强 DiT；(2) 矩形检测框与八边形初始化怎么衔接。

---

## 1. 我对项目现状的认识

### 1.1 主线 pipeline（V8.2 基线）

- 骨干：`heatmap_resnet`（ResNet34），stride-4 特征图，既出检测（CenterNet 式 ct heatmap + wh）也供 snake/DiT 采点。
- 初始化：检测 box → `get_quadrangle`（框四边中点为伪极点）→ 极点 refine 头（`use_extreme_refine`，`ct_snake.py:809-857`）预测 4 个真极点 → `get_octagon` 构八边形 → 上采样 128 点。
- DiT/flow matching（`flow_matching_evolution.py`）：学的是**位移场**。初始八边形是坐标系原点 + 特征采样位置（沿轮廓 grid_sample 点特征 concat 进 DiT token），flow 的随机起点是位移空间的高斯噪声。
- 基线成绩（64 样本，pred_det + pred_ext）：**mean IoU 0.7075**（init 0.6478），step 37500。

### 1.2 Locate 系实验（V10 / V10.1 / V10.2 / V8.3a）已做了什么

| 实验 | 方案 | 结果 |
|---|---|---|
| V10 joint | 小号 MoonViT（6层/384）从零训，端到端 | IoU **0.2052**（step2000，远未收敛） |
| V10.1 | 真 Locate vision tower（27层/1152）**冻结**，输入 cap 224，取最后一层 token，1152→64 conv 投影，双线性插值到 stride-4，检测头+DiT 都吃这个特征 | 端到端 IoU **0.3689**（init 0.3817），step 20000 后 OOM 中断 |
| V10.1 + GT init | 同上，但用 GT 极点八边形初始化，剥离检测质量 | init **0.7775** → final **0.6989**，**diffusion 负收益 -0.079** |
| V10.2 boxoct | V10.1 基础上改 `diffusion_init_source: 'gt_box_octagon'`（GT 框中点伪极点→八边形） | init 0.6761 → final 0.6648，同样负收益（仅 step500） |
| V8.3a | 只训 DiT、关检测，单测 Locate 特征 | OOM 中断（~step1000） |

### 1.3 关键诊断：性能下降的主因不是训练不足

**证据一（检测/初始化）**：端到端 init IoU 只有 0.38（基线 0.65）。在冻结的低分辨率特征上从零训一个 CenterNet 头，20k 步训不好不奇怪——这部分确实有训练量因素，但更根本的问题在证据二。

**证据二（特征质量，这是决定性的）**：GT init 隔离实验里，初始轮廓已经是 0.7775，DiT 跑完反而掉到 0.6989。**训练不足只能解释"涨得少"，解释不了"系统性变负"**——基线同口径下 diffusion 是正收益。说明 DiT 在 Locate 特征上采不到细化轮廓所需的边界信息。

**根因分析——分辨率瓶颈**：当前取特征的方式是
`输入 cap 到 224 → patch=14 → 16×16 个 token → 最后一层 → 1152→64 conv → 双线性插值到 stride-4`。

两个致命问题：

1. **空间分辨率**：16×16 的 token 网格意味着每个 token 覆盖原图 ~14×14（cap 后实际更粗）。轮廓细化需要 stride-4 级别的边界梯度信息，双线性插值不会凭空造出高频细节——DiT 沿轮廓采到的相邻点特征几乎是同一个 token 的插值，没有法向上的边界对比。
2. **层选择**：VLM vision tower 的最后一层是为语言对齐服务的，语义强、定位弱。检测（中心+尺寸）还能凑合，逐点轮廓回归需要的是中低层的边缘/纹理特征。

一句话：**Locate 的强项是"框在哪"的语义判断，它的（这样取出来的）特征恰恰不擅长"边界在哪"的逐像素判断。现在的集成方式是让它的短板（低分辨率语义特征）去干主线 ResNet34 的本职工作（高分辨率边界特征），同时还没用上它的长板（直接出框的检测能力）。**

## 2. 对两个核心问题的回答

### 问题 1：Locate 特征怎么取最好？

**原则：不要让 Locate 特征替代高分辨率 conv 特征，而是作为语义辅助注入。**

具体建议（按优先级）：

1. **保留 ResNet34（或同级 conv backbone）作为 DiT 的主特征源**。边界细化所需的 stride-4 高频特征由它提供，这是 V8.2 已验证有效的部分，不要动。
2. **Locate 特征作为附加的语义 condition 注入**，而不是唯一特征图：
   - 投影到与主特征相同通道数后，在 stride-4 处与主特征 **concat 或加权相加**（最简单，先做这个）；
   - 或者作为 DiT 的额外 cross-attention context（`dit_denoiser_v3_4.py` 已有 detail_feat 这种 zero-init 辅助上下文的先例，模式可复用，并且 zero-init 保证起点不低于基线）。
3. **如果一定要用 Locate 特征本身提分，先修两件事再谈结论**：
   - **提高输入分辨率**：`moonvit_max_input_size` 从 224 提到 448 以上（MoonViT 是原生分辨率架构，支持的；OOM 可用冻结骨干 + no_grad + 特征缓存解决，见 §4 E3）；
   - **取中间层而非最后一层**：抽 1/3、2/3 深度处的 hidden states 做多层融合，定位信息比最后一层强。
4. **验证协议**：所有特征方案先跑 **GT-init 隔离评测**（V8.3a 的思路是对的）。判据很干净：`final IoU > init IoU` 且 `final ≥ 基线同口径 final`，才说明特征有增益。端到端数字混杂了检测质量，不要先看它。

### 问题 2：矩形框 vs 八边形初始化，三选一还是有别的路？

先给结论：**三个选项都不选，因为你需要的桥梁在代码库里已经存在了——极点 refine 头。** 推荐方案：

> **Locate 出框（它最擅长的事）→ 框四边中点构伪极点菱形（`get_quadrangle`，现成）→ 极点 refine 头预测真极点（`use_extreme_refine`，现成，有 GT 极点监督）→ `get_octagon` 构八边形 → DiT。**

逐条说明为什么不选另外三条路：

- **重新探索矩形初始化**：不必。历史经验（V2→V3）和现在的数据都支持八边形：V10.2 的 GT 框八边形 init 是 0.676，而 GT 极点八边形 init 是 0.778——**极点信息值约 0.1 init IoU**。回到矩形是放弃这 0.1，方向反了。
- **把 Locate 改成出极点**：代价最高、风险最大。Locate 是 VLM，改输出头意味着重新微调一个 2B 级模型，而且极点预测本质是个轻量局部任务，用一个小 Snake-GCN 头在框内做就够了（DeepSnake 原版就是这么设计的，`evolve.py` 的 init_gcn 就是干这个的）。杀鸡不用牛刀。
- **设计算法把矩形变八边形 + 重新预训练**：方向对了一半，但"纯几何算法"（V10.2 的 boxoct 就是）的上限就是 0.676——框中点不是真极点，几何构造补不回形状信息。**要用可学习的极点头，不是固定算法**。

这个方案的额外好处：
1. 极点 refine 头已经实现并接好了监督（`diffusion_trainer.py` 的 ex loss，目标 `i_gt_4py`），不需要新代码，只需要在训练时给它喂"框抖动"增强（模拟 Locate 框的误差分布）；
2. 它跑在**主 conv 特征**上（高分辨率），不受 Locate 特征分辨率问题影响；
3. 检测与分割彻底解耦：Locate 可以完全离线推理出框（甚至预计算成 json，V9 的 teacher 路线就是这个形态），训练时主网络不需要背着 27 层 ViT。

### 关于"是否需要重新预训练"

需要，但不是从零。当前 DiT 预训练时初始轮廓来自 **GT 极点八边形**，而部署时初始轮廓来自"Locate 框 → 预测极点八边形"，存在 init 分布偏移。建议预训练/续训时用**混合初始化**：

- 70% GT 极点八边形（保底，维持已有能力）；
- 30% "GT 框加噪声抖动 → 极点头预测 → 八边形"（模拟部署分布；`use_pred_extreme_init_for_diffusion` 开关已存在）。

从 V8.2 checkpoint 续训即可，不必重训 1 万轮从零开始。

## 3. 推荐总体架构

```
                       ┌────────────────────────────┐
   image ───────────►  │ LocateAnything（冻结/离线） │ ──► 检测框（可预计算缓存）
        │              └────────────────────────────┘          │
        │                         │ (可选, 第二阶段)            ▼
        │                         ▼                      框→伪极点菱形(get_quadrangle)
        │              中间层特征, ≥448输入                      │
        │                         │                            ▼
        ▼                         ▼                      极点refine头(use_extreme_refine)
   ResNet34 (stride-4) ──► [concat/cross-attn 注入] ──►        │
   主特征，负责边界          语义辅助，zero-init               ▼
        │                                              极点八边形(get_octagon)
        │                                                      │
        └──────────────► DiT flow matching  ◄──────────────────┘
                          (沿轮廓采点特征)
```

核心思想：**Locate 管"在哪"（检测，离线、冻结），conv 管"边界长什么样"（高分辨率特征），极点头管"框到八边形的翻译"，Locate 特征注入是锦上添花的第二阶段，且必须过 GT-init 隔离评测才算数。**

## 4. 分阶段实验计划（按"先便宜先解耦"排序）

### E1 — Locate 检测质量摸底（不训练，半天）
对验证集跑 Locate 推理出框，和 GT 框、以及 V8.2 当前检测头的框分别算 IoU/召回。
**目的**：确认"Locate 检测确实更强"这个前提。如果它在这批数据上框得并不比现有检测头好，后面一切都要重估。
产出：一个 boxes json（顺便就是 E2 和 V9 teacher 路线需要的缓存，注意 V9 引用的 `data/eagle_teacher/1232_final_train_locateinit.json` 目前在磁盘上不存在，正好补上）。

### E2 — Locate 框 + 现有 V8.2 网络，纯推理评测（不训练，半天）
用 E1 的框替换 V8.2 推理时的检测输出，走"框→伪极点→极点 refine 头→八边形→DiT"全链路评测。
**目的**：量化"只换检测、其他全不动"能拿到多少分。这是整个 Locate 路线最便宜的收益验证。
预期：如果 E1 显示 Locate 框更好，这里 init IoU 应明显超过 0.6478，端到端应超过 0.7075。

### E3 — 极点头的框抖动适配 + 混合 init 续训（小训练，1-2 天）
从 V8.2 checkpoint 续训：极点 refine 头加框抖动增强，DiT 用 §2 的 70/30 混合初始化。评测仍分 GT-init / Locate-box-init 两口径。
**目的**：消除 init 分布偏移，把 E2 的收益固化。

### E4 — Locate 特征注入消融（第二阶段，确认 E2/E3 后再做）
前置修复：`moonvit_max_input_size` ≥448、抽中间层、冻结骨干 no_grad + **离线特征缓存**（特征是冻结的，逐样本预计算存盘，训练时直接读——同时根治 V10.1/V8.3a 的 OOM）。
注入方式：stride-4 concat（zero-init 投影）起步。
**判据**：GT-init 口径下 final > init 且 ≥ 基线，才保留；否则放弃特征注入，只保留 Locate 检测（E2/E3 的收益已经独立成立）。

### 暂停项
- V10/V10.1 式"Locate 特征独挑大梁 + 检测头从零训"的路线建议暂停——GT-init 负收益已经说明该取法下特征本身不行，继续加训练步数大概率是沉没成本。
- V10.2 纯几何 boxoct 路线被 E2/E3 的"可学习极点头"方案取代。

## 实验结果更新（2026-06-12）

**E1 完成**：框数对齐口径（~32 框/图，177 张 test），Locate 全面优于 V8.2 检测头：mean IoU 0.688 vs 0.610，recall@0.5 0.807 vs 0.752，precision@0.5 0.825 vs 0.740。前提成立。报告：`data/eagle_teacher/e1_locate_vs_v8_2_detection_report.*`。

**E2 完成**：V8.2 权重 + Locate 框走现有链路：init 0.591 / final 0.634；V8.2 自检测同口径（conf0.3 框数对齐）init 0.571 / final 0.609。Locate 框已领先，但距 GT 极点 init（0.78）仍有大 gap → 极点头不适配真实框分布，E3 修。

**E3 完成**：框抖动（scale±10%/shift±5%）+ 30% pred 极点混合 init，从 V8.2 step42000 续训至 50000。最佳 checkpoint step_47000：

| 口径 | V8.2 基线 | E3 step47000 | Δ |
|---|---|---|---|
| Locate 框 init/final | 0.591/0.634 | 0.597/**0.655** | +0.021 final |
| 自检测 conf0.01 init/final | 0.632/0.676 | 0.640/**0.703** | +0.027 final |

final 涨幅 > init 涨幅，证实混合 init 提升了 DiT 对不完美初始化的修复能力。step50000 与 47000 持平，无需更久。
顺带修复了 MoE `_last_aux_loss` 持计算图导致的显存泄漏（这也是 V10.1/V8.3a 历史 OOM 的根因）。

**E4 完成（2026-06-12）**：特征缓存（9+18 层、448 输入、fp16、5.5GB，`data/locate_feat_cache/`）；zero-init adapter 注入，从 E3 step47000 权重续训至 55000（途中第二次 OOM：locate_feat 提前上 GPU + dtype 双副本，已修，加 `PYTORCH_CUDA_ALLOC_CONF=max_split_size_mb:128`）。

E4 step55000 vs E3 step47000（177 张 test）：

| 口径 | E3（无注入） | E4（注入） | Δ |
|---|---|---|---|
| Locate 框 init/final | 0.597 / 0.655 | 0.601 / **0.662** | +0.007 final |
| 自检测 conf0.01 init/final | 0.640 / 0.703 | 0.654 / **0.713** | +0.014 init / +0.010 final |
| **GT-init 隔离** final | **0.8375** | 0.8335 | -0.004 |

**E4 裁决**：按文档判据，GT-init 口径 E4 略低于 E3（-0.004，接近噪声），说明 Locate 特征对 **DiT 轮廓细化本身没有增益**；但端到端两口径 E4 均更好，增益来自**检测头 init 质量提升**（自检测 init +0.014）。修正后的高分辨率中间层取法至少消除了 V10.1 时代的负收益（当年 GT-init 下 diffusion -0.079，现在 GT-init final 0.83 远高于 GT 八边形 init ~0.78，diffusion 是健康正收益）。

**最终结论与推荐配置**：
1. **部署主推 E4 step_55000**（`data/outputs/e4_locate_feat_inject_gpu2/checkpoints/`）：两个部署口径全面最优。若追求架构简洁可用 E3 step_47000，只损失约 0.007-0.010。
2. 预训练问题的主要收益来自 **E3 的混合初始化/框抖动**（final +0.021~0.027），其次是 E4 特征注入（+0.007~0.010，来自检测侧）。
3. Locate 作为检测器的路线成立（E1 框质量全面占优 + E2/E3 链路适配），"Locate 特征强化 DiT" 这条当初师兄建议的路在正确取法下也只有检测侧收益——**不必再投入 DiT 侧特征融合的进一步探索**，下一步提分方向应该是检测头/极点头本身。

## 累计修复的基础设施问题
- MoE `_last_aux_loss` 持计算图 → 跨 step 显存泄漏（V10.1/V8.3a 历史 OOM 根因）
- E4 locate_feat 提前上 GPU + dtype 双副本 → 第二类泄漏
- E1 检测对比的"多框灌水"口径问题（已建立框数对齐 + 一对一 precision 的公平协议）

## 5. 风险与备注

1. **E1 是整个计划的阀门**：所有后续投入都建立在"Locate 框确实更准"上，先验证再花训练资源。
2. **OOM 问题**（V10.1 step20571、V8.3a 均崩）：根源是 27 层 ViT 即使冻结也在前向时占大量激活显存。E4 的离线特征缓存是正解；joint 训练时背着它没有必要。
3. **未提交代码**：当前 `ct_snake.py`（+567 行）、`diffusion_trainer.py`（+135 行）等 Locate 集成代码均未 commit。建议先提交一版，再开始 E 系列实验，否则结果无法对应代码版本。
4. 本文中所有基线/实验数字来自 `visual/` 下的 eval json（64 或 32 样本子集），做最终结论时应在完整测试集上复验。
