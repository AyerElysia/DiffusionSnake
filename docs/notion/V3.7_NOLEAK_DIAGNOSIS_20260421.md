# V3.7 no-leak 泛化掉点诊断（2026-04-21）

## 结论

这次 `btcv_diffusion_dit_v3_7_v6b_full_noleak` 的掉点，**不是训练没收敛**，而是“正式 no-leak 主线并没有真正复现 standalone V6b 的关键机制”。

### 已确认的核心问题

1. **`scale conditioning` 在正式主线里没有真正生效**
   - 配置里虽然开了 `v3_7_use_scale_conditioning: true`
   - 但 `FlowMatchingEvolution.predict_velocity()` 之前没有把 `contour_scale` 传给 denoiser
   - 结果：full no-leak 训练/推理时，V6b 最关键的尺度条件分支实际上是空跑的

2. **正式主线缺少 V6b 的 per-contour normalization**
   - standalone V5b/V5f/V6/V6b 都用了：`x1_norm = x1_raw / contour_scale`
   - 正式主线之前仍然走的是全局 `diffusion_disp_stats` 归一化
   - 对多器官、多尺寸轮廓来说，这会弱化复杂小结构和后续 contour 的细节恢复

3. **正式主线缺少 V6b 的采样策略**
   - standalone V6b：`t ~ Beta(0.3, 1.0)` + `zero_x0_prob=0.5`
   - 正式主线之前：`t ~ Uniform(0,1)` + 全随机高斯 `x0`
   - 这会让训练目标更平均，但也更容易得到“平滑但保守”的解

## `v6g`：detail-context 结构分支的最新结论

为了解决上面的 detail underfit，新增了一个 **resume-safe detail-context 分支**：

- 文件：
  - `lib/networks/diffusion/dit_denoiser_v3_7.py`
  - `lib/networks/diffusion/flow_matching_evolution.py`
- 配置：

  - `configs/btcv_diffusion_dit_v3_7_v6g_full_noleak_detailctx_only.yaml`

核心做法：

- 沿 contour 法向做多偏移 feature sampling
- 构造局部 detail 特征后送入 zero-init 的 detail projection
- 这样旧 checkpoint 加载时几乎不改变原行为，可以安全续训

### warm-start 验证

`v6g` 直接加载 `v6d epoch395` 的前 14 个样本切片几乎不变：

- `v6g warm-start`: `0.8721709`
- `v6d latest`: `0.8721631`

说明新分支初始化时是近似 identity 的，**结构接入本身安全**。

### 关键新发现：旧 resume 策略会给新分支“假阴性”

最初直接按旧方式续训 `v6g` 时，看起来几乎没有改善。进一步排查后确认：

- 旧 checkpoint 会把 `optimizer + scheduler + step` 一起恢复
- `v6d epoch395` 此时学习率已经在 cosine 尾段，只有 `~4e-8`
- 对 zero-init 的新 detail 分支来说，这等于几乎没有真正训练

因此新增了训练逻辑开关：

- `resume_weights_only: true`

对应代码：

- `diffusion_train.py`

含义：

- 只加载模型权重
- 不恢复 optimizer / scheduler / global step
- 让新结构从 fresh LR 重新开始学习

### 当前判断

到目前为止，可以比较清楚地说：

1. `v6d` 的 detail failure **不是单纯“再训久一点”**
2. `normal-direction detail-context` 这个方向 **不是完全没用**
   - 它能在不破坏整体切片均值的情况下，给部分样本带来小幅提升
3. 但它 **还不足以解决用户最关心的 hardest contour**
   - `idx_013` 的最后一条复杂 contour 依然是主要瓶颈

因此下一步更值得考虑的，不是继续盲目拉 epoch，而是针对这类 contour 继续改结构，例如：

- 加入 **tangent-direction / along-curve context**
- 改善复杂 contour 的 **point parameterization / resampling**
- 或者对 hardest contour 引入更强的局部几何约束
   - stage B: 再单独引入 `contour_norm`
   - stage C: 最后再评估 `Beta-t / zero-x0`

## 关键判断

这次掉点的本质不是：

- “V6b 思路错了”
- 或者“scale conditioning 没价值”

而是：

> **正式 no-leak 训练并没有真正跑到 standalone V6b 的方法本体。**

所以当前最值得做的，不是盲目换网络，而是先把 **V6b 的有效机制完整迁回正式主线**，再看它在 full no-leak 下的真实上限。

## 2026-04-21 深夜补充：runtime 采样 bug 修复 + `v6l` 参数化实验

### 1. 修掉了一个真实的 runtime 参数化 bug

在 `lib/utils/snake/snake_gcn_utils.py::uniform_upsample()` 的 PyTorch fallback 里，原来对 `k>1` 的边使用了：

- `torch.linspace(..., steps=k)[:-1]`

这会导致：

- 每条边实际只生成 `k-1` 个点
- 最后再用尾点重复 padding 补齐到 `p_num`

也就是说运行时存在：

> **少采样 + 尾点重复补齐**

这是一个真实 bug，已经修复为：

- `torch.linspace(..., steps=k+1)[:-1]`

不过后续复测表明：

- 这个 bug **不是当前 `eval_v37_full_iou.py` 指标变化的主导来源**
- 修复后现有 `v6d / v6k` 指标与 `idx_013` 基本不变

> 这是必须修的正确性问题，但**不是本轮 detail failure 的主因**。

## 2026-04-22 凌晨补充：V3.4 式 multistep 恢复到当前 FM 主线

用户提醒是对的：`V3.4` 时期验证过 **多步训练 + 多步推理** 很重要，而当前 `v6` 主线里这件事实际上被“配置层面关掉了”。

### 1. 真实情况：代码没删，但主线配置没开

排查后确认：

- `FlowMatchingEvolution` 里其实一直保留着：
  - 训练时的 random-start multi-step target 构造
  - 推理时的 `sample_disp_iterative()`
- 但当前 `v6k / v6l` 等主线配置都没有打开：
  - `use_iterative_refinement: true`

也就是说：

> 不是功能消失了，而是我们最近这条泛化主线一直在按 **single-step FM** 跑。

### 2. 又发现了一个实验陷阱：旧版 full-val evaluator 会绕过 multistep

进一步排查时发现：

- `scripts/eval_v37_full_iou.py`

旧实现里直接手工调用：

- `core.gcn.sample_disp(...)`

这会导致：

> 即使 config 打开了 `use_iterative_refinement: true`，  
> 评估脚本也**不会真正走 multistep 推理分支**。

这也是为什么最开始把 multistep config 套到 `v6k / v6l` checkpoint 上时，切片结果“完全不变”。

这不是模型问题，而是 evaluator 绕过了正确前向逻辑。

已经修复：

- `scripts/eval_v37_full_iou.py`
  - 当 `use_iterative_refinement=true` 时：
    - 调 `sample_disp_iterative()`
    - 读取 `iterative_num_steps`
    - 读取 `iterative_fractions`
    - 读取 `iterative_ode_steps`

### 3. 为了真正对齐 3.4 语义，又补了 iterative ODE 配置

为了让当前 FM 路径能更自然地复用 `V3.4` 的多步思路，新增：

- `lib/config/config.py`
  - `iterative_ode_steps = 0`
- `lib/networks/diffusion/flow_matching_evolution.py`
  - multistep 推理优先读取：
    - `iterative_ode_steps`
    - 若未设置则 fallback 到 `iterative_ddim_steps`
    - 再 fallback 到 `flow_ode_steps`

这样当前 FM 主线也能表达：

> **外层 3-step iterative refinement + 每一步内部更细的 ODE 求解**
