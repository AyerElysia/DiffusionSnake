## 三、v6b 拐弯泛化失败根因分析

### 根因 1：训练对齐偏差（Greedy Alignment）⭐ 最关键

**位置**：`lib/networks/diffusion/flow_matching_evolution.py`，`forward()` 中轮廓对齐逻辑

**现象**：训练时将 v6b 的初始轮廓与 GT 对齐，只做：
```
oct[0] → 找最近的 GT 点 → 以此 shift 对齐整条轮廓
```

**问题**：对于 C4/C5 级别的复杂拐弯轮廓（如 idx_013），真正的最优相移（optimal cyclic shift）可能偏离 10~30 个点。贪心算法找到的 shift 只对第一个点合理，整条轮廓的其余点，尤其是拐弯区域，对应的训练目标（velocity field）是系统性错误的。

网络在大量"对齐错误"的样本上反复训练，泛化时遇到真实拐弯就会失效。

**修复方案**：`v6s` 配置中 `v3_7_optimal_cyclic_align: true`：
```python
# 遍历所有 128 个相移，取 MSE 最小的那个
best_shift = argmin_over_128_shifts(MSE(oct_shifted, gt))
```
O(N²) 复杂度，N=128 时可接受。

---

### 根因 2：Patch 全局上下文分辨率不足 ⭐ 已有实验证据

**架构**：
```
P2 feature map: 128×128×64
→ 分成 16×16 = 256 个 patch（每 patch = 8×8 像素）
→ DiT 接收 256 个 patch token 做注意力
```

**问题**：一个跨越 10~15px 的尖锐拐弯，在 patch 表示中只占 1~2 个 token（8×8px/token），细节严重被平滑。DiT 拿到的拐弯信息已经是失真后的版本。

**证据**：
- V7_v6bq（query 模式，无 detail context）= **0.893**
- v6o（patch 模式，有 detail context + endpoint loss）= 0.8919

Query 模式（Perceiver 式，256 个可学习 query 对完整 128×128 feature map 做 cross-attention）天然有更高的有效分辨率，且比额外增加 detail context 采样更简洁有效。

---

### 根因 3：曲率重加权 Loss 从未启用 ⚠️ 低成本未测试

**位置**：`lib/networks/diffusion/flow_matching_evolution.py`，`compute_curvature_weights()` 方法

**代码已实现**：
```python
def compute_curvature_weights(self, gt_contour):
    # 计算每点曲率 → 高曲率点权重更大
    ...
```

**但所有泛化实验配置均为**：
```yaml
v3_7_use_curvature_reweight: false
```

直线段与拐弯段在 loss 中权重相同，模型没有动力特别精准拟合拐弯。  
这个 flag 在单样本过拟合实验中也从未测过，是完全空白的改进点。

---

### 根因 4：HF Loss 权重偏低

```yaml
v3_7_hf_loss_weight: 0.1   # 相对于主 FM loss 1.0
```

拐弯是高频信号，0.1 的权重使高频误差对总 loss 的贡献极小。可尝试 0.3~0.5。

---

### 根因 5：Detail Context 覆盖范围不足（次要）

v6g~v6o 的 detail context 采样方式：
```
对每个轮廓点，沿法线/切线方向采样，radius = clamp(scale/64, 0.75, 2.0) px
```

在高曲率拐弯处，法线方向 1.5~2px 的采样可能：
- 穿越器官边界落在错误区域
- 3-wide curve context 窗口（前/当前/后一个点）无法感知跨越 10+ 点的弯曲形状

## 四、V3.10 架构配置问题（确认 Bug）

### 问题描述

`configs/btcv_diffusion_dit_v3_10.yaml` 中：
```yaml
use_dit_v3: true
use_dit_v3_1: true
```

但 `FlowMatchingEvolution.__init__()` 中的架构选择逻辑为：
```python
if getattr(cfg, 'use_dit_v3_7', False):      # ← 检查 v3_7
    self.denoiser = DiTFlowMatchingV3_7(...)
elif getattr(cfg, 'use_dit_v3_6', False):     # ← 检查 v3_6
    ...
elif getattr(cfg, 'use_dit_v3_2', False):     # ← 检查 v3_2
    ...
else:                                          # ← 默认 fallback
    self.denoiser = DiTFlowMatchingV3_2(...)  # V3.2 架构
```

`use_dit_v3` 和 `use_dit_v3_1` **不在任何分支的判断条件里**。V3.10 会静默退化到 V3.2 默认架构，丢失所有 V3.7 改进：
- ❌ scale conditioning
- ❌ per-point output head
- ❌ detail context
- ❌ curve context
- ❌ 可学习 query 全局上下文

### 处置建议

**如果 V3.10 的目标是在 V3.7 基础上测试 adaptive points**：
```yaml
# 将以下两行
use_dit_v3: true
use_dit_v3_1: true
# 改为
use_dit_v3_7: true
```

**如果 V3.10 的目标是在旧架构（V3.1/V3.2）上独立测试 adaptive points**：行为是正确的，但应该在配置注释中写明，避免误解。

## 五、Adaptive Points（V3.10）实现现状

adaptive points 的实现散布在数据集层：
- `lib/datasets/coco/snake.py`：`compute_adaptive_points()` 根据 bbox 大小动态计算 `num_points`
- `lib/datasets/voc/snake.py`：同上
- `lib/datasets/collate_batch.py`：动态 batch 下的变长序列处理

相关 flag：
```yaml
adaptive_points_enabled: true   # lib/config/config.py 默认为 false
```

**注意**：BTCV 数据集的采样器（`lib/datasets/btcv/`）是否已接入 `compute_adaptive_points()` 需单独确认，COCO/VOC 有实现，BTCV 未在本次分析中看到明确对接代码。
